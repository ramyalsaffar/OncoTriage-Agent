# WHY THIS FILE IS HERE AND NOT ONLY IN THE SIBLING TREE (item 21)
# ----------------------------------------------------------------------------
# The Dockerfile's build context is "03- Code" (docker-compose.yml sets
# `context: .`), and a COPY may not reach outside its context. The old Dockerfile
# said
#
#     COPY 05-*Requirements/requirements.txt /app/requirements.txt
#
# and NOTHING IN THE BUILD CONTEXT HAS EVER MATCHED THAT PATTERN. The dependency
# list lives at "{project root}/07- Requirements/requirements.txt", one level
# ABOVE the context, under a different number. So the build failed at that line
# on every checkout this repository has ever had. Nobody hit it because
# `docker compose build` never got that far: compose validated the file first and
# died on an undefined network (item 21, defect 1).
#
# Only "03- Code" is version-controlled. On a clean checkout there is no
# "07- Requirements" and no sibling tree at all, so an image that depends on one
# cannot be built from a clean checkout by definition. That is what put this file
# inside the code directory.
#
# THE DIRECTORY NAME IS LOAD-BEARING. `oncotriage/paths.py` sets the Docker
# branch's `requirements_path` to "/app/requirements/", and the Dockerfile copies
# the code tree to /app, so this file lands at exactly the location that path
# variable names. Before item 21 that path named a directory nothing created, on
# any code path, ever.
#
# THE DUPLICATION IS REAL AND IS THE TOP-RANKED FOLLOW-UP. Two files now carry a
# dependency list — this one and "07- Requirements/requirements.txt" — and
# nothing checks that they agree. The right end state is one list, in
# `pyproject.toml`, with `pip install .` as the only installer; `pyproject.toml`
# declines to do that today and says why ("needs the versions pinned from a
# working environment, not guessed"). Item 21 supplies exactly that measurement
# — see below — so the merge is now unblocked. It is not done here because it
# changes how the package installs for every consumer, not just the container.
#
# WHERE THESE VERSIONS COME FROM, and why they are not the old ones
# ----------------------------------------------------------------------------
# Every pin below was READ OUT OF THE INTERPRETER THIS PROJECT IS DEVELOPED AND
# RUN ON (`pip list`, 2026-08-06, Python 3.13.5), not carried forward from the
# old file and not guessed. The old pins were dated "February 2026" and had
# drifted badly from the environment the code is actually exercised in:
#
#     package                old pin      measured      note
#     ---------------------  -----------  ------------  -----------------------
#     langgraph              0.2.59       1.0.8         MAJOR version apart
#     torch                  2.5.1        2.9.0
#     transformers           4.47.1       4.57.1
#     sentence-transformers  3.3.1        5.2.2         MAJOR version apart
#     openai                 1.58.1       1.99.9
#     qdrant-client          1.12.1       1.16.2
#     streamlit              1.41.1       1.45.1
#     fastapi                0.115.6      0.117.1
#     uvicorn                0.34.0       0.40.0
#     pydantic               2.10.4       2.12.5
#     numpy                  2.0.2        2.1.3
#     scipy                  1.14.1       1.15.3
#     pendulum               3.0.0        3.2.0
#     python-dotenv          1.0.1        1.1.0
#     python-multipart       0.0.20       0.0.22
#     python-dateutil        2.9.0        2.9.0.post0
#
# Installing the old set would have produced an environment this code has never
# run in, which is a strange thing for the only reproducible artefact in the
# project to contain.
#

#   * fastembed  — `oncotriage/embedding.py` is the one construction site for
#                  `SparseTextEmbedding("Qdrant/bm25")`, the sparse encoder that
#                  BOTH halves of BM25 retrieval depend on. "01- Imports.py"

#
#     streamlit    1.45.1        requires packaging >=20,<25
#     apache-airflow-core 3.1.7  requires packaging >=25.0
#
# There is no version of `packaging` that satisfies both, so pip refuses the
# combination outright ("ResolutionImpossible") — measured by building this
# image with 1.45.1 pinned. The development machine has both installed anyway,
# with packaging 26.0, and `pip check` there says so in as many words:
#
#     streamlit 1.45.1 has requirement packaging<25,>=20, but you have
#     packaging 26.0
#
# So the dashboard on that machine is running against a `packaging` its own
# metadata declares incompatible. That is a real finding about the development
# environment, not about the container, and it is reported rather than papered
# over.
#
# 1.46.0 is the SMALLEST step that resolves: it relaxes the cap to
# `packaging<26`, which leaves packaging 25.x satisfying Airflow's `>=25` and
# streamlit's `<26` at once. Later streamlit releases (1.61.1 drops the upper
# bound entirely) would also resolve, and were not chosen: the dashboard code
# was written against 1.45.x, and `tests/test_package_invariants.py` check 6b asserts
# against a PRIVATE streamlit internal (`cache_utils._make_function_key`), which
# is exactly the kind of thing a sixteen-minor-version jump breaks.
